## Misses

### 1. `/recipes/new` first-load JS 156.3 kB, over 150 kB (Must fix)

- **Evidence:** Lighthouse `network-requests` on `/recipes/new` loads 5 scripts, 157.2 kB
  transferred: `index` 88.6, `recipeQueries` 47.2, `RecipeForm` 19.2, `NewRecipePage` 1.3,
  runtime 0.9. Vite's gzip sizes sum to 156.3 kB. On this route the form chunk is not
  deferred work: nothing useful paints without it.
- **Cause, by chunk** (source maps of the same build):
  - `index-*.js` 89 kB: `react-dom` (~71% of its source), `@tanstack/query-core`, and the
    **Radix `AlertDialog`** with `react-remove-scroll`, `react-dismissable-layer`, `tslib`
    (`client/src/features/recipes/DeleteRecipeButton.tsx:3`, `import { AlertDialog } from
    "radix-ui"`). The dialog is only used after a click on Delete on `/recipes/:id`, but it is
    in every route's first load: about 14 kB gzip measured on its own (esbuild, React
    external).
  - `recipeQueries-*.js` 47 kB: `zod` (~44%) and `react-router` (~43%). Zod is there because
    `recipeQueries.ts` parses responses with `RecipeListSchema` / `RecipeSchema` from
    `@pinch/shared`.
  - `RecipeForm-*.js` 19 kB: `@tanstack/form-core` (~69%), plus `@tanstack/devtools-event-client`
    and `@tanstack/pacer-lite` pulled in by TanStack Form.
- **Fix (smallest first):** load the delete confirmation only when it is needed. Either
  replace the Radix `AlertDialog` with a native `<dialog>` + `showModal()` (focus trap, Esc and
  inert background are built in; `role="alertdialog"` + `aria-labelledby`/`aria-describedby`
  on it), or keep Radix and `lazy()` the dialog body behind the Delete click. Either takes
  ~14 kB off every route: `/recipes/new` to ~142 kB, `/` and `/recipes/:id` to ~123 kB.
  Re-measure after. (Moving `@pinch/shared` to `zod/mini` would save more but touches every
  schema; not worth it for 7 kB.)

### 2. `/recipes/new` mobile LCP 2.13 s, over 2.0 s (Must fix)

- **Evidence:** `largest-contentful-paint` 2133 / 2131 / 2133 ms in three runs (score 0.95).
  `lcp-breakdown-insight`: the LCP element is the form's intro paragraph,
  `form.mt-6 > p.text-sm` "A title, the ingredients and the steps are all a recipe needs."
  (`client/src/features/recipes/RecipeForm.tsx`, the `<p>` before the fields), with TTFB 2 ms
  and the rest element render delay. FCP is 0.75 s: the page paints Layout's "Loading…" at
  the same time as `/`, then waits.
- **Cause:** a chain of three serial JS fetches before the LCP text exists. The entry
  chunks (137 kB) load and run, `lazy()` then requests `NewRecipePage`, which then requests
  `RecipeForm` (`client/src/App.tsx:10`, `NewRecipePage.tsx` imports `RecipeForm`).
  Under Lighthouse's mobile throttling (150 ms RTT, 1.6 Mbps) the second round trip plus
  19 kB costs ~1.4 s. The heading "New recipe" is in the lazy page chunk too, so nothing of
  the page itself paints early.
- **Fix:** paint the page's own text from the entry bundle and lazy-load only the form. Make
  `NewRecipePage` a normal import in `App.tsx` (it is 0.6 kB), move the intro paragraph out of
  `RecipeForm` into the pages (beside the `<h1>`), and wrap a `lazy(RecipeForm)` in
  `<Suspense>` inside the page. The heading and intro then paint with the first render, as
  `/` does at 0.75 s; the form's own text (labels) is smaller and would not become the LCP.
  Fix 1 also helps: 14 kB less on the critical path is ~70 ms on that profile.

## Worth doing (within budget)

- **`/recipes/:id` mobile LCP 1.96 s, 40 ms under budget.** The LCP element is the
  description `<p>` (`article > p.mt-3`), shown only after the entry JS runs and then
  `GET /api/recipes/:id` returns (a JS → data waterfall). Fix 1 above takes ~70 ms off it. A
  longer recipe title or description would not change it; a heavier first bundle would push
  it over. Keep the 137 kB entry from growing.
- **`unused-javascript` 74–81 KiB** on every route (the Radix dialog, zod parsers and the
  router code not used by the current page). Fix 1 removes the biggest piece that is not
  needed at first paint.
- **The list query is a collection scan with an in-memory sort.** `explain` of
  `find({ ownerId }).sort({ createdAt: -1, _id: -1 }).limit(50)`: `SORT` over `COLLSCAN`,
  124 docs examined for 50 returned; the only index is `_id`. 5 ms today. The design's index
  `{ ownerId: 1, createdAt: -1, _id: -1 }` (`docs/system-design.md:237`) needs the
  `db:indexes` script that is still to come; land it with cursor pagination in M3.
- **`e2e/a11y.spec.ts` does not scan `/recipes/:id` or the open delete dialog.** The observer
  scan found 0 violations there today; add both to the spec so a regression fails the run.
- **Render-blocking CSS** (`render-blocking-insight`): `index-*.css`, 3.6 kB, est. 140–150 ms
  on mobile. Unchanged since M1; leave it.
- **Agentic Browsing 50** (not in the budgets): `llms-txt`, `ard-schema`. No action.

## Carried from M1

- **pino-http logs every request and response header: still open.** `server/src/app.ts:18`
  is `app.use(pinoHttp({ logger }))` with no `redact` or custom serializers. Each request line
  carries the 13–14 request headers (`user-agent`, `referer`, `sec-ch-*`, `if-none-match` …)
  and all 13 helmet response headers: 1.4 kB per line on average in the observer log, 1.7 kB
  in the e2e log. Request bodies are not logged (good). Still Worth doing, and **Must fix
  before auth lands (M7)**: `pinoHttp({ logger, redact: ["req.headers.cookie",
  "req.headers.authorization", 'res.headers["set-cookie"]'] })`, or serializers that keep
  only method, URL, status and time (which would also cut the line to ~250 bytes).
- **"One bundle" note: resolved, and it reached the threshold.** M1 said to split with
  `lazy()` only if first-load JS neared 150 kB. M2 added `react-router`, `zod` (response
  parsing), Radix and TanStack Form; the form was split out (`App.tsx:8`, with that reason in
  its comment), and the entry is now 136.8 kB (+39 kB). The split keeps `/` and
  `/recipes/:id` in budget but not `/recipes/new` (Miss 1).
