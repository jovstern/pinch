## Worth doing (within budget)

1. **`/recipes/:id` mobile LCP 1.95 s: 45 ms under the budget, +150 ms since M2.** The most
   likely next miss.
   - **Evidence:** same recipe (a description, like M2's), same API, same machine: the M2 tip's
     build (ec9cda3) gives 1804 / 1813 / 1818 ms; HEAD's gives 1954 / 1957 / 1954 ms
     (`largest-contentful-paint`; Performance 99, `interactive` also flagged). LCP element is
     the description `article > p.mt-3` (on a recipe without one, the second step
     `article > ol > li`), shown after the entry JS runs and `GET /api/recipes/:id` returns.
     Unthrottled, the page is the same as in M2 (observed LCP 76 ms vs 73–79; main-thread work
     264 vs 253 ms; `bootup-time` of `index` 94 vs 97 ms).
   - **Cause:** the JS → data waterfall from M2, now with a 3.0 kB larger entry on its critical
     path. Main-thread time didn't change, so the 150 ms jump is Lighthouse's simulated network:
     a step that size looks like one more simulated round trip (150 ms RTT on mobile) to fetch
     the bigger entry. This is inferred from the A/B, not traced. `/` and `/recipes/new` are
     unaffected: their LCP is text painted with the first render.
   - **Fix, by impact:** (a) take list-only code out of the entry: `RecipeListPage` with
     `ListFilters` behind one `lazy()`, like `LazyRecipeForm`, keeping the heading outside so
     `/` still paints at FCP (check `/` LCP after); or (b) start `GET /api/recipes/:id` before
     React renders (`queryClient.prefetchQuery` in `main.tsx` when the path is a recipe), so the
     fetch doesn't wait for the router to mount. Either keeps the next milestone's code from
     pushing this route over 2.0 s.
2. **`/recipes/new` first-load JS 147.2 kB: 2.8 kB under 150 kB.** Same cause, same fix as 1(a):
   every kB in the entry counts against this route too. M4 (imports) will add UI to the entry;
   measure this route in every slice that grows it.
3. **`e2e/a11y.spec.ts` gained no coverage in M3.** It still scans only `/` and `/recipes/new`
   with errors; only its wait changed (it now waits for the sample recipes). Add
   `/?q=…&tags=…` (search and tag filters), `/recipes/:id`, the open delete dialog and
   `/recipes/:id/edit` with tag chips. The observer scan found 0 violations on all of them, so
   the tests would pass today and catch a regression later.
4. **Text search sorts every match in memory.** `?q=eggs` read 171 index keys and documents to
   return 50 (`SORT` over `TEXT_MATCH`); 7 ms p95 here. It grows with how many of my recipes
   match one word, not with the collection, and is capped by Mongo's 100 MB sort memory. Fine
   for one cook's recipes; note it in design §7 if it isn't there.
5. **A two-tag filter uses the index for the first tag only** (multikey bounds; the second is
   checked in `FETCH`). Here both tags were common, so nothing was wasted; with a rare second
   tag it reads every recipe with the first tag. As `indexes.ts` says; nothing to do now.
6. **`unused-javascript` 63–72 KiB** (`index` 42 of 86 KiB, `api` 20 of 37 KiB on
   `/recipes/:id`). Same story as M2; 1(a) cuts part of it.
7. **Render-blocking CSS** (`render-blocking-insight`, est. 150 ms on mobile): `index-*.css`,
   4.1 kB. Unchanged; leave it.
8. **Agentic Browsing 50** (not in the budgets): `llms-txt`, `ard-schema`. No action.

## Carried from M2

- **pino-http logs every request and response header: still open.** `server/src/app.ts:18` is
  still `app.use(pinoHttp({ logger }))` with no `redact` or serializers. Median line 1.3 kB in
  the observer log, 1.7 kB in the e2e log. Still Worth doing, and **Must fix before auth lands
  (M7)**: `pinoHttp({ logger, redact: ["req.headers.cookie", "req.headers.authorization",
