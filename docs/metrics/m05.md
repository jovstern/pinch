## Worth doing (within budget)

1. **The import's progress `step` is never set** (spec gap, now visible). Design §1 requirement 4
   and §4.2 say the user sees `waiting → fetching → analyzing → ready`, and
   `ImportList.tsx:115–116` shows "Fetching the video…" and "Reading the recipe…" for it. No
   server code writes `step` (`server/src/worker/workLoop.ts`, `geminiExtract.ts`), so a link
   shows "Working on it…" for the whole 9–21 s. Set `step: "fetching"` before `readVideoInfo`
   and `step: "analyzing"` before `askGemini` (a fenced `updateOne` like the others), or take the
   requirement out of the design.
2. **The worker logs no timings and no Gemini usage.** "import ready" has `importId` and
   `attempt` only. With a paid API, log the attempt's duration, the `yt-dlp` and Gemini parts,
   and `response.usageMetadata` (prompt/candidate/total tokens) on each Gemini call. That is how
   cost and slow imports would be seen after M7.
3. **`/recipes/:id` with its delete button is 1.0 kB under the 165 kB budget**, `/` 14.6 kB.
   M4's split (a) (`RecipeListPage` behind `lazy()`, its `<h1>` kept in the route) takes about
   20 kB off `/recipes/:id`, if M6 or M7 add client code.
4. **`GET /api/imports` sends every ready import's whole draft** (carried from M4, now bigger).
   Gemini's drafts here were 0.8, 1.2 and 3.5 kB, against about 0.6 kB for the fake. A list
   of 20 ready cake-sized drafts is about 70 kB per change (304s are unaffected). Leave `draft`
   out of the list (a projection); the review page gets it from `GET /api/imports/:id`.
5. **`/imports/:id` LCP 1.96 s, 43 ms under** (carried): the LCP is drawn only after
   `GET /api/imports/:id`, because `ReviewImportPage.tsx:57` returns "Loading the recipe…" while
   pending. Draw the `<h1>` above the pending branch (the not-ready one, line 67, has its own).
6. **`/recipes/:id` LCP 1.96 s, 45 ms under** (carried): start `GET /api/recipes/:id` in
   `main.tsx` before React renders (M3's fix (b)).
7. **`e2e/a11y.spec.ts` still scans only `/` and `/recipes/new`** (carried from M3). M5 added
   `e2e/text.spec.ts` but no axe coverage of the text import, the review page or the recipe page
   with nutrition. The observer scan passes on all of them today.
8. **pino-http logs every header (carried from M2, Must fix before M7):** `server/src/app.ts:19`
   is still `app.use(pinoHttp({ logger }))`. Median line 1676 B in the e2e log (1333 B average
   in the observer log). Fix as in m03: `redact`, or serializers that keep method, URL, status
   and time.
9. **The e2e worker log still loses its shutdown lines** (carried, M4 point 7): this run's
   `e2e-worker.log` ends at the last "import ready".
10. **`spike/links.txt` is tracked in git** (`git ls-files spike` lists it). It holds the
    spike's Instagram, Facebook and YouTube links; if they are not meant to be public, remove it
    from the index and ignore it.
11. Render-blocking CSS (est. 150 ms) and Agentic Browsing (`llms-txt`, `ard-schema`): unchanged;
    no action.
