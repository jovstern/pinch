## The font

- **Size and loading:** `client/public/fonts/fraunces.woff2` is 29,500 B (29,820 B transferred).
  `client/index.html` preloads it; every run shows it requested first, at High priority, about
  6 ms after the document, before the JS. `font-display: swap`; Lighthouse's
  `font-display-insight` passes.
- **CLS:** none. 0.000 on every mobile run, ≤ 0.0003 desktop (as in M5), with the font and
  without its preload.
- **LCP on `/`:** none. 0.76 s as in M5. The LCP there is the box's hint, in the system font,
  drawn before any API answer.
- **LCP on `/recipes/:id`, `/imports/:id`, `/recipes/:id/cook`:** **it costs about 450 ms in
  Lighthouse's simulation.** I served each commit's build against the same API and data and
  loaded the seed recipe, which has no picture, so only the client changed:

  | Build                                         | `/recipes/:id` LCP, mobile (2 runs) |
  | --------------------------------------------- | ----------------------------------- |
  | 4df0619, M5 merged, before U4                 | 1964, 1956 ms                       |
  | 41745a5, U4 done (the font, preloaded)        | 2409, 2405 ms                       |
  | af24481, U2 done (cook mode)                  | 2413, 2406 ms                       |
  | 763174d, thumbnails in the client             | 2419, 2407 ms                       |
  | 6b1cd64 / c68c214                             | 2404–2412 ms                        |

  The jump comes with U4 and nothing after it adds to it. These pages draw their LCP only after
  `GET /api/recipes/:id` comes back, which needs the JS first. The font's 30 kB loads alongside
  that JS on the throttled 1.6 Mbps link and pushes it later. With real (DevTools) throttling the
  same comparison is 2766 → 2910 ms, +150 ms, about 30 kB at that speed. Lantern overstates it,
  but both methods say the font slows these pages.
- **What doesn't help:** taking the preload out alone (2.41 s; the wordmark's CSS asks for the
  font at about 55 ms anyway). The plan's fallback, loading it only on the recipe and cook routes
  (`docs/ux/plan.md` U4), would not help either: those are the routes it slows, and `/` doesn't
  feel it.
- **Against the JS budget:** a font isn't first-load JS. The U4 plan says the font "must fit the
  165 kB SPA budget with the entry". Counted that way it doesn't: 153.1 + 29.5 = 182.6 kB on `/`.
  The user answered "Fraunces is worth it" (`docs/ux/plan.md` §9, 2026-11-09). I report it here
  and don't count it as a miss: the user accepted the bytes, but the LCP above isn't accepted yet.

## Misses

### Miss 1 (Must fix): LCP on the data pages, 2.26–2.41 s against 2.0 s

`/recipes/:id` (with or without a picture) and `/imports/:id` are 2.41 s, and `/recipes/:id/cook`
is 2.26 s. In M5 the first two were 45 and 43 ms under (`m05.md` Worth doing 5 and 6). Two causes
add up, each measured:

1. **The font (U4), about +300–450 ms** on every page that waits for the API (above).
2. **The picture is one more round trip** on `/recipes/:id` and `/imports/:id`: HTML → JS →
   `GET /api/…/:id` → `GET /api/…/:id/thumbnail`. Lighthouse's `lcp-discovery-insight` fails
   ("Request is discoverable in initial document: no"; "fetchpriority=high should be applied:
   no"); the image is `Thumbnail.tsx`'s `<img loading="eager">`, rendered from `RecipePage.tsx:37`
   and `ReviewImportPage.tsx:82`. With the font taken out of the critical path, a recipe without a
   picture comes to 2.11 s and one with a picture stays at 2.41 s.

Experiments on 6b1cd64's build, served against the same API (2 mobile runs each, in ms):

| Variant (scratch build, not committed)                                        | `/:id` none | `/:id` picture | `/imports/:id` | `/cook` | `/`      |
| ----------------------------------------------------------------------------- | ----------- | -------------- | -------------- | ------- | -------- |
| As built                                                                      | 2406        | 2405           | 2407           | 2256    | 756      |
| No preload link only                                                          | 2408        | 2406           | 2256           | 2264    | 756      |
| Font loaded by JS 2.5 s after `load` (`@font-face` and preload taken out)     | 2106–2119   | 2405           | 2107–2406      | 2108    | 756      |
| `<link rel="preload" as="fetch">` of the recipe's JSON in `index.html`        | 2255–2260   | 2258           | —              | —       | —        |
| `RecipeListPage` behind `lazy()` (`/:id` JS 144.1 kB)                          | 2256–2264   | 2256           | 2420–2425      | 2107    | **2440** |
| Lazy list + preloaded JSON                                                    | 2109–2114   | —              | —              | —       | —        |

No single change gets under 2.0 s. Making `RecipeListPage` lazy makes `/` miss (its LCP text
moves into the lazy chunk), so I don't recommend it. Fixes, ranked by impact:

1. **Take the font off the critical path.** Load it after the page's first data has drawn: a
   `FontFace` added from `main.tsx` after `load` or idle, instead of the `@font-face` rule and the
   preload in `client/index.html:11`. This saves about 300 ms on every data page. CLS stayed 0.000
   in the experiment, but titles will then swap visibly on a slow first visit. A fallback
   `@font-face` with `size-adjust` / `ascent-override` on Georgia keeps the swap from moving
   anything. After the first visit the font is cached, so the swap only happens once.
2. **Start the recipe's (or draft's) request in `index.html`,** not after the JS: a few lines of
   inline script that, on `/recipes/:id[/cook|/edit]` and `/imports/:id`, start `fetch` of the
   JSON and, when it names a `thumbnail`, add `<link rel="preload" as="image" fetchpriority="high">`
   for it. The query's `queryFn` takes that promise the first time. The JSON preload alone gave
   −150 ms. This also removes the picture's extra round trip, which nothing else here does; I
   could not measure that part without changing the client's code. Add `fetchpriority="high"` to
   the `full` thumbnail (`Thumbnail.tsx`) in the same change.
3. **Fetch the delete dialog's chunk on intent, not on load** (Miss 2's fix): 13.7 kB less on the
   same throttled link.

My estimate is that 1 + 2 bring every data page under 2.0 s, but I measured the parts and not
the whole. Measure again after the fix. **Or accept it with the reason written here:**
all four pages are under 2.5 s (Core Web Vitals' "good"), Performance is 98–99, and a
budget for these pages could be set at 2.5 s, as the JS budget was raised in M4.

- `history.csv` keeps M2–M5's convention for `/recipes/:id`: the entry before the recipe shows
  (153.1 kB), not the 166.8 kB with the delete chunk that this miss is about.
- **Cause:** U2 crossed the budget, and M6 added to it. When cook mode became its own chunk,
  rolldown moved `recipeQueries.ts` and TanStack Query's core (shared by the entry, `CookPage` and
  `DeleteRecipeButton`) into a new `recipeQueries` chunk. The entry fell 2.30 kB and the new chunk
  is 3.25 kB: the chunk boundary costs 0.95 kB of compression. Then the thumbnails added +0.52 kB
  (`Thumbnail.tsx`, the schema), the screenshots +0.85 kB (`ScreenshotsUpload.tsx`, `sendForm`),
  and HEAD +0.10 kB. The cook chunk itself (4.5 kB) is not loaded on `/recipes/:id`.
- **Fix (smallest):** load the delete dialog when the user reaches for it, not when the recipe
  opens. `LazyDeleteRecipeButton.tsx` renders `<DeleteRecipeButton>` right away, so its 13.7 kB
  (Radix AlertDialog, which `react-vite.md` requires) arrives with every recipe. Render a plain
  "Delete" button that starts `import("./DeleteRecipeButton.tsx")` on `pointerenter`/`focus` and
  opens the dialog when it's there. Then `/recipes/:id` is 153.1 kB, 11.9 kB under, and the LCP
  page loses 13.7 kB on the critical path (Miss 1, 3).
- Alternative: keep `recipeQueries` in the entry (a `manualChunks`/`advancedChunks` rule): −0.95 kB,
  not enough on its own.
