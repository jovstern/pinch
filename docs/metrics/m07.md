# M7 (polish) metrics

Measured 2026-11-09 on branch `m7-states`, commit **beef6f0** (the a11y e2e). Everything was built
and run from a `git archive` of that commit in a scratch folder (the repo's `node_modules` linked
in, `@pinch/shared` pointed at the archive's own `shared/`), never from the working tree. The tree
had uncommitted changes while I measured (`DeleteRecipeButton.tsx`, `RecipePage.tsx`,
`globals.css`, the cook files, `stepText.ts` → `ranges.ts`); **they are not in these numbers.**

Setup: the production build served by `vite preview` on port 4710, its own API on 3710 and its
own fake-extractor worker, on a `pinch-test-observer-m7` database (indexes + the 10 sample
recipes; dropped afterwards). Pictures were made the way the worker makes them, without Gemini:
two screenshot imports of a real YouTube frame (`i.ytimg.com`, 1280×720, and a 1080×1920 crop of
it), turned into thumbnails by the fake worker with the real `shrink` (281×500 WebP 5,408 B;
400×225); both approved, and a third portrait screenshot kept as a draft. Lighthouse 13.6.0,
headless Chrome, default (simulated) throttling; mobile is the median of 3 runs, desktop 1 run.
"Change" is against `m06.md`. The dev servers (3000, 5173), the user's worker and the `pinch`
database were not touched; no Gemini call was made. A UI reviewer ran at the same time on its own
ports (3310/4310), which may add a little noise to the API p95s (not to Lighthouse's simulated
numbers).

Routes: `/` (12 recipes, 2 with pictures; imports: 1 screenshot draft with its picture, a ready
Instagram link, a ready text, a failed text), `/?q=lentils&tags=fit:comfort`, `/recipes/new`,
`/recipes/:id` with the 281×500 picture and the seed "Red lentil soup" with none, `/imports/:id`
(the portrait screenshot draft), `/recipes/:id/cook` (the seed recipe).

## Budgets: which are met

Met: Performance, Accessibility, Best Practices, SEO (every route, both form factors), CLS, TBT,
**first-load JS on every route** (M6's Miss 2 is fixed: `/recipes/:id` is 153.8 kB, 11.2 kB
under), axe, console errors, API p95 reads and writes, 5xx, and the LCP of `/`, `/?q=…` and
`/recipes/new`.

Not met, as measured: **LCP on the four data pages, 2.11–2.12 s against 2.0 s**, 106–117 ms
over (M6: 2.26–2.41 s). The branch gives exactly what the experiments predicted (≈ 2.11 s).

**Decided (the user, 2026-11-09): (b).** The data pages' budget is now 2.5 s, written in the
metrics skill's table; they meet it with 380–390 ms to spare, so every budget is met.

## Miss 1 (accepted: the budget is 2.5 s): data-page LCP 2.11 s against 2.0 s

What M7 changed, measured: the font now loads at `load` + 1.5 s, after every page's LCP in
Lighthouse's trace, so it is out of the LCP graph (−300 ms on `/recipes/:id` and `/imports/:id`,
−150 ms on cook), and the size-matched Georgia fallback keeps CLS at 0.000 through the swap.
`fetchpriority=high` is on the full thumbnail (`lcp-discovery-insight` now says "fetchpriority=high
applied: yes"). The delete dialog no longer loads with the recipe. The review page starts
`RecipeForm` on mount (its chunk now comes in beside the draft's JSON, at ≈ 57 ms in the trace,
not after it).

What is left is round trips, not bytes. Each data page is three in a row:

- `/recipes/:id`: HTML → entry JS (110 kB) → `GET /api/recipes/:id` → (with a picture) the
  thumbnail. `lcp-discovery-insight`: "Request is discoverable in initial document: no".
- `/imports/:id`: HTML → JS → the draft's JSON and `RecipeForm` (side by side) → the thumbnail.
- `/recipes/:id/cook`: HTML → JS → `CookPage` chunk, with the recipe's JSON beside it.
  The breakdown is all "element render delay" (413 ms in the unthrottled trace).

### The question was: (a) start the JSON in `index.html`, or (b) accept 2.5 s (decided: b)

I built option (a) in a scratch copy of the client (not committed) and measured it against the
same API and data, 3 mobile runs each. The inline script in `index.html` matches
`/recipes/:id[/cook|/edit]` and `/imports/:id`, starts `fetch` of the JSON into
`window.__early`, and when the answer names a `thumbnail` adds `<link rel="preload" as="image"
fetchpriority="high">` for it; `getJson` (`client/src/lib/api.ts:19`) takes that promise the
first time. Lighthouse shows one JSON request at ≈ 11 ms and the thumbnail at ≈ 20–25 ms.

| Variant (scratch build)                                                  | `/:id` picture   | `/:id` none      | `/imports/:id`               | `/cook`          |
| ------------------------------------------------------------------------ | ---------------- | ---------------- | ---------------------------- | ---------------- |
| As built (beef6f0)                                                       | 2109 2111 2109   | 2106 2107 2107   | 2117 2116 2117               | 2105 2113 2106   |
| (a) inline script: early JSON + picture preload                           | 1959 1956 1955   | 1956 1961 1956   | 2129 2129 2129               | 2107 2110 2107   |
| (a) + the route's lazy chunk `modulepreload`ed by the same script         | 1955 1955 1954   | —                | 2105 **1955** 2104           | 1954 1956 1956   |

- (a) alone brings **only the recipe page** under 2.0 s, by **≈ 40–45 ms**. It does nothing for
  `/imports/:id` and cook: there the third round trip is a lazy chunk (`RecipeForm`, `CookPage`),
  not the data.
- Fixing those needs the script to also `modulepreload` the route's chunk, whose name is hashed
  at build time, so a Vite plugin (`transformIndexHtml`) or the build manifest has to write it
  in. Cook then gets 1.95 s; the review page is still 2.10 s in 2 of 3 runs (Lantern ties the
  picture to the entry JS when the JSON finishes after it), so it doesn't reliably pass either.
- Its costs: an inline script (≈ 0.3 kB gzip in every HTML), a global the app reads, a branch in
  `getJson` with its own fallback and tests, a CSP hash once the app has a CSP, and for cook and
  review a build plugin. All to save 150 ms in a simulated metric, with a margin of 45 ms that
  the next feature on these pages can take back.

**Recommendation: (b), accept 2.5 s for the four data pages** (pages that draw their content
from an API answer after the JS: `/recipes/:id`, `/recipes/:id/edit`, `/recipes/:id/cook`,
`/imports/:id`) and keep 2.0 s for every other route. The numbers: the data pages are 2.11–
2.12 s mobile (390 ms under 2.5 s, Core Web Vitals' "good"), 0.49 s desktop, Performance 99, CLS
0, TBT 0; and M7 already took 150–300 ms off them. Option (a) passes only one of the four pages
reliably, with a 45 ms margin, and costs the most indirect code in the client, against the
project's "simplicity above all". If the user still wants the recipe page under 2.0 s, (a) for
`/recipes/:id` alone (no chunk preload, no plugin) is the cheap part: ≈ 20 lines, measured at
1.955–1.961 s. The budget change, if accepted, belongs in the metrics skill's table with the
reason written here, as the JS budget was raised in M4.
