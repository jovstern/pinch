### What each fix did

1. **The entry as one file** (`vite.config.ts`: `build.rolldownOptions.output.codeSplitting.groups
   = [{ name: "index", tags: ["$initial"] }]`). Why `lib` split: Rolldown puts each module in a
   chunk by the set of chunks that import it, so react-router's modules that the entry shares with
   the lazy Log in and Sign up (and the editor, ⋯) got a set of their own, a new 6.6 kB chunk;
   the imports were already written the same way everywhere (`"react-router"`), so there was no
   import to change. The same rule had already cut the entry into 17 files (react, zod, TanStack
   Query, …). The `$initial` group puts every module the entry statically needs in the entry's
   own chunk: 1 file instead of 17, and 6.8 kB less gzip (fewer chunk wrappers). Lazy chunks still
   carry only what they add. It removes 16 requests from the start-up burst (HTTP/1.1, 6
   connections): every data page gains 0.37–0.45 s, which is more than M9 had added. Cook: 2.67 →
   **2.30 s**, under 2.5 with 0.2 to spare; no other cause is left over budget.
2. **`/` with an empty queue** (`LazyImportForm.tsx`): the Suspense fallback shows "Paste a video or
   a recipe" in the same 46 px box, after the sparkles' 36 px, so the LCP text paints with the
   entry: 2.78 → **0.76 s**, CLS 0.
3. **Log in** (`Wordmark.tsx`): the wordmark is an inline `<svg>` (`currentColor` in the accent, so
   light and dark from one path; `logo.svg`'s path rounded to one decimal, 1.8 kB gzip, the same
   shape at 40 px), in the lazy auth chunk. The text is the LCP: 2.86 → **0.76 s**. The auth
   pages' first load: 179.7 kB of 190.
4. **Signed out, no 401s**: `me` answers 200 `null`; a `pinch_signed_in` hint cookie (not HttpOnly,
   set with the session, cleared by logout and by any answer without a live session, and restored
   by `me` for an older session) lets `index.html`'s inline script preload `/api/imports`, and
   `main.tsx` wait for it on `/`, only when signed in. No CSP is set, so the inline script needs
   nothing; a CSP would need its hash. Console, signed out (`/`, `/login`, `/signup`, `/recipes`):
   **clean** (was 2 errors and a warning per load). A hint left without a session (the session
   expired) costs one 401 and one unused preload, once: that answer clears the hint.

**Console**, signed in, the 8 routes above with the hint: clean. `GET /api/auth/me`: p50 / p95
2.5 / 3.2 ms signed in, 1.5 / 1.7 ms signed out (50 warm requests). No 5xx.

**e2e**: 29 tests (M9's demo, `e2e/accounts.spec.ts`, added), twice green. The e2e API now runs

## Miss 1: `/` with an empty queue, 2.78 s (budget 2.0)

**This was not caused by M9.** Commit `4013aff` ("the empty queue's words hidden for now", 12:34
on 11-11) came after m08's last measurement of this page (0.75 s, #92). It hid the empty state's
text, which `LazyImportForm.tsx` still calls "the page's LCP". With that text gone, the largest text
on the page is the paste box's placeholder, "Paste a video or a recipe" (`ImportForm.tsx:146`), which
is inside the lazy `ImportForm` chunk.

Lighthouse's `lcp-breakdown-insight` names `div#placeholder`, with an element render delay of 416 ms
observed. Lantern adds the chunk's own round trip (`ImportForm` + `FieldError`, fetched at 85 ms in
the trace) to the HTML → JS chain, which gives 2.63 s before M9. M9's request at start-up (below)
makes it 2.78 s.

**Fix, measured.** Put the placeholder's words in the Suspense fallback (`LazyImportForm.tsx:14`), in
the same box, so that the same text paints from the entry:
```tsx
<div aria-hidden="true" className="flex h-11.5 items-center rounded-control border border-input bg-card px-3 text-text-muted">Paste a video or a recipe</div>
```
In a variant build on the same API and data, `/` with an empty queue measured **0.76 s** (756 / 755 /
757), CLS 0, Performance 100. That is one line. Bringing the empty state's words back would also
work.

## Miss 2: `/login`, 2.86 s (budget 2.0)

The LCP is the wordmark `<img src="/logo.svg">` in `AuthFrame.tsx`. Its box is 99×40 px, larger
than the page's text: "Log in" in the `h1` is short, and so is the footer. React renders the image,
so Lantern hangs its request off the entry's JS: HTML → JS → `/api/auth/me` (the `SessionGate`
waits) → the lazy `LoginPage` chunk → the image. `/signup` is the same frame, but its footer text
("Already have an account? Log in") is larger than the logo. That text is its LCP, at 0.75 s.

**Fix, measured in part.** Draw the wordmark as an inline `<svg>`, which is not an LCP candidate. A
variant build gave `/login` **2.14 s** (1990 / 2138 / 2142), with the `h1` as the LCP. That is still
0.14 s over 2.0 s, and this run did not isolate why Lantern ties this `h1` to the lazy chunk's chain
while `/signup`'s text gets 0.75 s.

Both pages render nothing until `/api/auth/me` answers (`SessionGate.tsx`: `if (isPending) return
null`). That makes them data pages, so the 2.5 s budget fits them. **For the user to decide:** inline
the logo and give `/login` and `/signup` the 2.5 s data-page budget, which `/login` meets at 2.14 s.
Note that inlining the 9.3 kB SVG grows `AuthFrame`'s chunk; the measured variant's first load was
191.6 KiB transferred against 187.3. An SVG component with only the paths keeps that small.

## Miss 3: cook, 2.67 s (budget 2.5), and what M9 adds to every page (+0.14 to +0.18 s)

Cook's LCP is the `h1` (text, a data page). It was 2.46 s at m08-fix and 2.53 s in today's control
(this machine reads about 0.05 s slower today), and 2.67 s with M9. Every page that waits on data
moved the same way against the control:

| Page | control | M9 | Δ |
| --- | --- | --- | --- |
| a recipe | 2.49 | 2.65 | +0.17 |
| cook | 2.53 | 2.67 | +0.14 |
| edit | 2.72 | 2.90 | +0.18 |
| a draft's review | 2.72 | 2.90 | +0.18 |
| `/`, empty | 2.63 | 2.78 | +0.14 |

**Where the time comes from.** Taken from the two waterfalls; not isolated by a variant build in
this run. M9 adds two requests to the start-up burst that every page shares on `vite preview`
(HTTP/1.1, 6 connections):
- the `<link rel="preload" href="/api/auth/me">` in `index.html` (A3);
- a new 6.6 kB shared chunk, `lib-*.js`. It holds react-router's code, split out of `index` because
  the lazy Log in and Sign up pages share it.

The entry also grows by 2.8 kB (the session gate, the avatar, `authQueries`). The HTML's first burst
is now 21 requests (19 in the control): 2 preloaded fetches, 17 scripts and the CSS. On top of that,
the app now gates on `me`. The gate costs no extra round trip, thanks to the preload, but its answer
must arrive before anything renders.

**Fixes, ranked:**
1. **Fold the `lib` chunk back into the entry.** In `build.rollupOptions.output`, give react-router a
   chunk name of its own, or merge it into `index`. That is one request less in the first burst, and
   probably about half of the +0.15 s. Estimated, not measured.
2. **Cook: start the recipe's request earlier.** It is not preloaded, so cook waits on HTML → JS →
   recipe. `/`'s pattern applies: a `queueKnown`-style head start, or a preload of
   `/api/recipes/:id` from `index.html` on recipe addresses, which needs a small inline script.
   Estimated −0.1 to −0.2 s.
3. **Or accept it.** On HTTP/2, which a host uses, the start-up burst does not queue (m08: about
   −0.8 s on the recipe page). The user decides.

## Miss 4: Best Practices 96 and console errors on the signed-out pages

`index.html` preloads `/api/imports` and `/api/auth/me` on every address. Signed out, both answer
401, Chrome logs each one as `Failed to load resource … 401`, and Lighthouse's `errors-in-console`
scores 0. The `/api/imports` answer is never used there, so Chrome also warns "preloaded using link
preload but not used within a few seconds". The e2e allows the 401s by name (`a11y.spec.ts`,
`expectedConsoleErrors`).

**Fix:**
- (a) `GET /api/auth/me` answers 200 with `null` when signed out, rather than 401. Signed out is an
  expected state, not an error. This is a small API and client change, and design §8.3 must say it
  too.
- (b) Preload `/api/imports` only for a signed-in browser, from a tiny inline script in
  `index.html` that adds the `<link>` when a non-HttpOnly `pinch_signed_in=1` hint cookie (set and
  cleared with the session) is present. Alternatively, accept the one 401 on signed-out loads.

(a) + (b) give Best Practices 100 and an empty console. (a) alone leaves one 401 and the warning.

## Worth doing (within budget)

1. **`/` with six pictures is at 2.995 s of 3.0** (one run 3.011). The 0.07 s since m08 is M9's
   start-up cost (Miss 3). Fix 1 there is this page's margin too.
2. **The editor's JS is at 188.1 of 190 kB** (+3.4 in M9). The next feature in the entry or in
   `RecipeForm` crosses it. `FieldError` (16.5 kB, TanStack Form) is now shared by the paste box,
   the editor and both auth pages.
3. **The e2e (and any setup that starts the API without `EXTRACTOR`) never takes the links cache's
   free path.**
   - The API compares the cache against `EXTRACTION[config.EXTRACTOR].version` (`index.ts:19`),
     and `playwright.config.ts` sets `EXTRACTOR: "fake"` only on the worker. So the API looks for
     Gemini's version while the fake worker writes `fake-1`.
   - In my run, with the API started the same way, 30 imports of cached links were all counted, and
     10 were refused with 429 at the daily cap. With `EXTRACTOR=fake` on the API, all 30 were free
     (202, p95 9.2 ms).
   - In production both are `gemini`, so the app is right. The free path (§4.6, D28) is just
     untested end to end. Setting `EXTRACTOR: "fake"` on the e2e API too is a one-line config
     change, so it needs the user's yes.
4. **`GET /api/recipes/count` p95 32.6 ms** (p50 4.5), the slowest read. It is a `countDocuments`
   on 20+ recipes and well within budget, but it is the one read with a tail. `GET /api/imports`
   p95 13.9 ms is next.
5. Carried from m08: `/api/imports` polled on every page; TanStack Form's devtools event client in
   production; card tiles download the full thumbnail; the e2e worker log loses its last lines; the
